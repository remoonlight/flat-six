## 收敛质疑与未闭合项

### 1. 权威需求与 ADR 不随项目下载，项目能独立交接吗？

目前不能据此认定完整交接。`git ls-files docs` 只列出 7 份 Markdown 和一份 JSON，而根 README、AGENTS 与规则依赖被忽略的 requirements/ADR。Git 跟踪的几份 OBD 旧说明反而比现行边界更容易随 clone 出现。

建议后续明确最小可同步集合：需求、ADR、总入口及不含私人环境信息的状态摘要；本机设备与历史日志继续本地保存。必须先逐文件检查隐私和来源，再调整忽略规则，不能直接取消整个 `/docs/` 忽略。本轮只澄清规则注释与入口中的下载缺口，没有扩大可提交范围。

闭合条件：在不携带 `.local/` 的干净 checkout 中，所有权威入口可读；私人设备信息、原始日志与厂商二进制仍被排除。

### 2. 菜单更少，是否意味着能力更清晰、验收更完整？

当前 `ObdPage.tsx` 的五个 Tab 与 OBD_STATUS 一致，但旧说明仍有“开发与验证”“广播记录”“维修对比”等入口。菜单移除只证明入口变化，不能证明底层能力已删除或后台 CLI 已覆盖全部交互。

`RepairComparePanel.tsx` 的引用搜索只找到它自己的导出，但 `scripts/steuer14-*`、数据库与 domain 仍存在维修对比相关功能和证据。它是待判断的保留实现，不能仅因页面不可达就删除整条链。应分别核对产品保留目标、IPC/数据库依赖和未来验收用途。

闭合条件：每个保留能力有明确入口或 CLI、持久化/恢复验证；每个退休能力有范围决定和依赖盘点，删除后没有悬空脚本。当前 OBD 汇总里旧生产 UI 验收的超时记录仍是未闭合证据，不能因脚本文件已修改而标为通过。

### 3. `accept:all` 真的覆盖“全部”吗？

当前 [编排脚本](../scripts/accept-all.mjs) 有 13 个 job；历史进度写过 11 个。它构建 domain/db 后运行业务验收，不包括全部 OBD/PIWIS UI、Python、desktop 类型检查或实车验证。

闭合条件：报告按变更涉及的能力列出实际 suite、结果与产物；“all” 仅指该脚本编排的集合。新桌面通信、VNCI 车辆读取、受限清码、写码与刷写分别保留验收缺口。

### 4. 981/982 合并目录会不会掩盖本车适用性？

166 个来源条目、299 个归档原件或大量跨变体定义，均是不同统计对象；不能相加、互换，也不是本车可执行功能数。合并导航仍须保留车系、硬件、软件、版本条件、PDK/手动挡差异以及未知状态。

闭合条件：准备清单绑定具体来源和适用条件；切换功能后旧规则失效；执行能力只由经过资格化的 ECU 和请求决定。不能用 982/991 资料补齐本车未知字段。

### 5. 把研究 Markdown 合成一份或删除生成清单，真的更可维护吗？

EPC 明文、逐码数据需求、车型手册与 PIWIS 文件索引可能包含相同零件或代码，但分别承担源证据、需求映射、原始车型语境和归档定位。按名称/代码去重会丢失来源、ECU、状态字节、适用性和版本。

闭合条件：只有职责和内容均重复的正文才合并；生成清单若替换，仍须可重建并保留来源定位。不能以精简 Markdown 为由删除私有原件、失败抓包或将跨车型同码直接合并。

### 6. 规则摘要变短，会不会把操作例外变成默认授权？

“只读”“不写 ECU”都不足以准确表达当前 ADR：具名受限清码是单独确认的例外，隐藏设码仍未形成可写闭环；历史 PETKA GUI 许可也只属于原会话。原子规则应引用当前 ADR，不能反复复制旧结论。

闭合条件：只读确认不授权清码；清码必须单独指定 ECU；未知发送/响应不重试；GUI 与委派授权不从历史材料继承。本轮只修正表述，没有新增现场许可。
