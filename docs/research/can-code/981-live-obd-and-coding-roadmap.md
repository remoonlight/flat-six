# 981 实时 OBD、扩展诊断与独立设码落地方案

核对日期：2026-09-12。对象：本项目的 2014 Boxster S（981）PDK。

实现设计见 [实时 OBD 与独立设码架构](../../obd-architecture.md)。用户最新状态为全部设备未连接，先推进架构及离线开发；本文的设备枚举为当时观察记录，不代表当前在线状态。

本文结合当前仓库和公开开发资料，回答如何由本项目直接连接车辆、辅助诊断，并逐步脱离 X431 执行已验证的特殊功能和设码。它是实施设计，不代表适配器或任何写车功能已经验证。

## 1. 结论与本次需求变化

可以先完成通用 OBD 读码、实时数据、记录回放和基于证据的诊断建议；981 多 ECU 诊断需要另建 ECU 定义；独立设码需要逐项建立并验证操作流程，不能用通用 PID 库替代。

用户这次明确新增“X431 辅助采集、以后本项目独立设码”的目标，超出旧 ADR 001 的产品范围。本轮将其记录为新增方向，未接车、未发诊断指令、未增加可执行写车代码。进入具体写车功能开发时，应同步修订 AGENTS、ADR 001、requirements 和 obd-plan 中旧边界，写明实际支持的功能和验证条件，避免文档与程序相互矛盾；不将“特殊功能”整体视为已验证。

设备链接：[淘宝商品 888839182701](https://item.taobao.com/item.htm?id=888839182701)。本轮网页读取失败，浏览器又受到站点安全策略阻止；**此商品的品牌、型号、所购 SKU、接口与 SDK 均未确认**，不把它假定为 ELM327、OBDLink、J2534 或 USB-CAN。不过用户随后确认另有 MX+、vLinker、Panda 等硬件，已足以确定首期适配路线，见下节。

## 1.1 按用户现有设备调整后的主路线

用户本轮确认拥有：X431、诊断 CAN 一分二线、PIWIS PT3G 专检套装、内网 CAN 线头、comma4（带 Panda 服务）、OBDLink MX+、vLinker FS BT。comma4 当前未连接。**用户指定 vLinker FS BT 为本项目主适配器；MX+ 已在内网承担 RaceChrono 通信采集，不调配到本项目。** 这里不把“拥有设备”写成“已连接车辆并验证”。

**先复用现有设备，不以新购硬件为前置条件：**

- **vLinker FS BT：首期与日常使用的主适配器。** Vgate 官方页面确认 Windows、HS-CAN/MS-CAN 和第三方软件支持，宣传请求长度可到 4K 字节。先核实 Windows 蓝牙配对后的出站 COM/RFCOMM 服务与实际 AT 命令兼容，再实现流控、长报文、重连和睡眠处理，不假定它支持 OBDLink 私有 ST 指令。页面中的 FORScan 设码/编程能力不能外推为 981 已支持；蓝牙标称 3 Mbps 也不是 ECU 实际采样率。[Vgate 官方 FS BT 页面](https://vgatemall.com/products-detail/i-52/)
- **OBDLink MX+：保留给现有 RaceChrono 链路。** 本项目不连接、重新配对、复位、改协议/过滤器或更新其固件。官方资料可作标准 OBD 实现参考，但不是本轮测试设备。[MX+ 官方规格](https://www.obdlink.com/products/obdlink-mxp/)、[开发资料](https://www.obdlink.com/developers/)
- **X431：实车模块、测量值与操作流程的主要对照。** 每次只研究一个模块/功能，导出或记录它实际产生的结果。
- **PIWIS + PT3G：第二对照与维修程序参考。** 本轮新增硬件方向允许把它作为研究参考，不把 PIWIS 软件纳入本产品依赖。PT3G 是需要进一步辨明的套装/接口型号，不能仅由名称认定存在可调用的 J2534 DLL。厂商文档也区分 PT3G 驱动模式和 J2534 设备接入。[TOPDON 官方连接说明](https://service.topdon.com/portal/zh/kb/articles/porsche-oem-software-with-rlink-connection-instructions)
- **comma4/Panda + 一分二：优先评估的旁路采集方案。** comma 官方将 Panda 描述为直接处理 CAN 的次级处理器，并提供公开收发 API。先核对设备上的服务究竟导出原始 CAN、诊断事务还是仅 openpilot 消息；不能把“有 Panda 服务”当作已存在可供 Windows 调用的 TCP/HTTP API。[comma 官方术语](https://docs.comma.ai/concepts/glossary/)、[Panda 官方仓库](https://github.com/commaai/panda)
- **内网 CAN 线头：保留作必要时的内部总线观测。** 需要确认它指车内 CAN 接线还是其他接口，并按 981 线束核对位置/引脚。首轮先使用诊断分线，不因有线头就跨接网关后的总线。

研究阶段的目标连接关系：车辆诊断口 → 一分二 → 一端 X431 **或** PT3G，另一端经核实的 Panda 接线 → comma4 本地采集 → Windows 导入。X431 和 PIWIS 不同时主动诊断，Panda 不参与发送。量产使用的目标关系：车辆诊断口 → vLinker FS BT → Windows 本项目；MX+ 继续服务原有 RaceChrono 链路。只有某项功能实测超出 vLinker 的传输能力时，才评估最终接口的替代方案，不默认占用 MX+。

首轮不依赖 RaceChrono 数据，也不把内网采集等同于诊断口采集。实施前确认 RaceChrono/MX+ 是仅监听广播还是也会主动请求，以及网关是否使两条路径共享 ECU 会话；据实际拓扑规划互斥，不能认为两个适配器就天然互不影响。X431/PT3G 抓包和 vLinker 主动诊断安排为不同会话，MX+ 配置保持现状。

comma4 若运行采集服务，只是离线/局域网采集外设；应用、知识库和 SQLite 仍留在 Windows。采集配置要核实未自动上传路线/车辆日志，不依赖 comma 云端。需要实时流时再实现有文档的本地桥接，不能假设 Windows 能直接经 USB 调用 comma4 内置 Panda。

### 本机只读枚举结果

2026-09-12 检查了 Windows PnP、串口及常见 J2534 注册项，未打开串口或发送 CAN/OBD 请求：

- COM1 是板载通信端口；COM6 的总线描述是 `Audio Radar`，不是已识别的 OBD。
- COM7 曾在线，USB ID 为 `303A:1001`、描述 `USB JTAG/serial debug unit`，后续枚举已不在线；不能据此判定商品型号。
- 此次设备枚举未发现可明确识别的在线 MX+、vLinker 或 Panda；这不否认用户拥有设备，也不能单凭 Windows 的连接状态判断蓝牙适配器是否可用。
- 检查了 HKLM 下原生/32 位的 PassThruSupport 04.04/05.00，未发现注册接口。这只说明当前电脑这些位置未注册，不证明 PT3G 无 SDK，也不代表专检电脑没有驱动。
- 用户明确 comma4 未连接，因此未尝试 SSH 或访问其服务。仍需具体适配器接通后完成链路确认。

### Panda 采集必须补的验证

官方当前代码区分 `SAFETY_SILENT` 与 `SAFETY_NOOUTPUT`：前者设置 CAN silent，后者没有开启 CAN silent。抓包要验证真实静默状态与服务是否会改变它，不能把“不发送应用报文”当作硬件完全被动。[Panda 安全模式实现](https://github.com/commaai/panda/blob/master/board/main.c)

另外，官方当前 Python `Panda()` 连接路径会调整通信设置，默认参数还可能关闭 heartbeat 检查；`can_recv()` 返回的解析记录没有逐帧硬件时间戳字段。实施时固定设备端固件/SDK 版本，先读本机服务代码与健康状态，避免盲目实例化第二个客户端抢占已有服务。日志区分采集主机接收时间和硬件时间，不把批次时间当成 ECU 精确响应时间；原始传输中的返回/拒发标志也须保留。[Panda Python 实现](https://github.com/commaai/panda/blob/master/python/__init__.py)

首期只有监听与离线回放；后续若要让 Panda 主动诊断，应另行设计受限服务/地址发送策略。不得为省事直接采用 README 中 unrestricted/allOutput 示例，更不能让诊断任务和驾驶控制任务同时控制该接口。

## 2. 项目真实起点

- `apps/desktop/src/pages/ObdPage.tsx` 已有连接、实时数据、故障码、就绪监控、分析、车辆信息和设码 Tab。但连接、刷新数据和硬件扫码按钮均禁用，车辆信息来自本地档案。
- `apps/desktop/electron/main.mjs`、`preload.cjs`、`db-bridge.mjs` 目前只有会话与码库相关 IPC，没有适配器传输、轮询或诊断协议实现。
- `packages/db/src/index.ts` 已有 `obd_sessions`、`obd_dtcs`；旧计划中的 `obd_samples` 尚未建表。当前 `dtc_kb` 以 `code` 单列为主键，不足以区分不同 ECU 对厂商码的解释。
- `data/seed/dtc/bootstrap.json` 有 49 条应用码库。`data/seed/dtc/manuals/by-code/codes.json` 另有 1112 个跨车型归档码，其中 981 覆盖 504 个；它们尚未进入应用码库，不能把 982/991 的描述或合并后的最优核验等级直接当作 981 证据。
- `data/seed/x431/981-2014-coding-menu.json` 有 34 个系统、78 条功能目录。`scripts/ingest-x431-rows.mjs` 根据菜单行生成通用人工剧本，未生成 CAN 地址、DID、字节位定义、解锁算法或执行状态机。
- 菜单含选装模块和“Tiptronic 变速器控制”等工具标签，**不等于这辆 PDK 车实装 34 个模块**。实车 ECU 身份必须另行读取。

因此工作量主要在通信与数据定义，不是把现有几个按钮启用。

## 3. 先确认适配器，才能选传输实现

vLinker FS BT 已定为首期目标，先核对实际固件和 Windows 接口。对于最初淘宝商品和 PT3G，仍需要从商品参数、说明书或卖家提供的公开开发资料确认：完整型号/硬件版本、固件版本、USB/蓝牙/Wi-Fi、Windows 驱动、开放 API、CAN/ISO-TP 支持、收发长度与时序限制。只标“支持保时捷”“支持全部 OBD 协议”不能证明第三方应用可以独立设码。下面说明不同接口的实现分支。

### ELM327 / STN 类

如果开放 AT/ST 指令，可由本地桥接程序通过 COM 或有文档的网络接口接入，先实现通用 OBD。ELM 数据手册提供设置 CAN 报头、过滤和流控等指令，因此不能断言这类设备物理上只能读；但具体型号的缓冲、长报文、时序和固件实现仍需要验证，不能由“ELM 兼容”推导出可替代 X431。[ELM327 手册](https://www.elmelectronics.com/wp-content/uploads/2017/01/ELM327DS.pdf)、[OBDLink 开发资料](https://www.obdlink.com/developers/)

USB/经典蓝牙 SPP 通常可走串口方案；BLE 需已知 GATT 服务/特征与分包协议，不能直接当作 COM；Wi-Fi 也需确认实际端点和应用协议。型号未定前，不预设端口、UUID、波特率或驱动下载地址。

### J2534 PassThru 类

如果厂家开放可独立调用的 Windows J2534 DLL，可做本地原生桥接，使用 CAN 或 ISO15765 通道。J2534 提供通信 API，不提供 Porsche 功能语义。不同厂家对引脚切换、监听和扩展的支持不同，不能套用另一家设备的能力。[Quantex 官方 PassThruConnect 文档](https://quantexlab.de/en/develop/j2534/pt_connect.html)

这是独立诊断/设码的优先评估路线之一；是否适合当前商品，取决于真实 DLL、协议支持及实测。桥接程序需匹配 DLL 的 x86/x64 位数，进程隔离避免驱动故障带走 Electron 主界面。

### 原始 USB-CAN 或封闭 VCI

原始 CAN 设备适合采集与定制协议，但需自己处理或引入 ISO-TP；不因 USB-CAN 名称就推定具备 K-Line 或可访问所有 ECU。封闭 VCI 若只供厂家 App 使用、无 SDK，则不能承诺本项目直接连接；要先解决公开接入接口，而不是继续填 UI。

## 4. 实时诊断应补哪些数据

### 4.1 第一批：标准 OBD，先探测支持再采样

建议支持以下服务，并分别记录成功、明确不支持、超时和无有效响应：

- Mode 01：支持 PID 位图、MIL/就绪状态与实时值。
- Mode 02：冻结帧，保留帧编号与关联故障信息。
- Mode 03 / 07 / 0A：已存储、待定、永久故障码；这些是通用排放诊断语义，不替代厂商 ECU 的完整状态位。
- Mode 09：VIN、标定信息等车辆实际支持的数据。
- Mode 06：监测测试结果，待确认各测试标识、单位和边界后增加，不能直接显示成“六缸失火计数”。

Mode 04 清码和 Mode 08 控制不属于只读采集；不放入第一批轮询。并非每台车支持全部 Mode。[OBD Solutions 服务说明](https://www.obdsol.com/knowledgebase/obd-software-development/obd-services-modes/)

第一组仪表使用转速、水温、车速、发动机负荷；第二组按支持情况加入进气温度、空气流量、节气门、两侧燃油修正、氧传感器/当量比和电压。转速 PID 0C 解码为 `(256*A+B)/4 rpm`，水温 PID 05 为 `A-40 °C`。每个响应都要先校验 ECU 来源、服务、PID 和有效长度。[OBD Solutions 实时数据示例](https://www.obdsol.com/knowledgebase/obd-software-development/reading-real-time-data/)

电压须区分适配器测得的供电电压与 ECU 上报值。机油温度、燃油轨压即使存在标准 PID，也须实际探测；PDK 离合器压力/磨损、各缸扩展失火计数、凸轮轴偏差等不可承诺通过通用 PID 获得。`python-OBD` 可作解码对照，其文档明确 Mode 06 实现仍有实车验证限制，不宜把库中有命令等同于本车可用。[python-OBD 命令表](https://python-obd.readthedocs.io/en/latest/Command%20Tables/)

轮询采用单个在途请求与优先级队列。界面刷新率和 ECU 采样率分开；每项展示最新采样时间、实际频率和过期状态，不承诺所有指标同时 10 Hz。

### 4.2 第二批：981 扩展诊断

先用 X431 获取实车 ECU 清单与硬件号、软件号、标定版本，选择 DME、PDK 等优先模块建立身份配置。随后才逐个添加地址、实际协议、扩展 DTC、测量值与冻结环境信息。UDS 是候选协议，不能据车型名称假定每个模块都使用同一协议、地址或安全等级。

对于确认采用 UDS 的模块，扩展读取通常涉及 ReadDTCInformation 与 ReadDataByIdentifier。解码需要车型/ECU 特定的 DID 定义、单位与布局；会话和超时也属于协议行为，必须实现响应待定等情况。[udsoncan 客户端文档](https://udsoncan.readthedocs.io/en/latest/udsoncan/client.html)

专业 Porsche 工具公开列出扩展实际值、模块诊断及部分设码能力，但也明确功能依模块/车型而异。这支持“按 ECU 建能力矩阵”的方法，不是本项目或淘宝商品已经兼容的证明。[Durametric 官方说明](https://www.durametric.com/)

### 4.3 “判断车辆问题”的产品结果

建议先做本地规则与维修资料检索，输出：已观测事实、可能原因、缺少的证据、下一步检查、相关部件位置、依据来源。使用已有故障台账和 Locator，把每条建议关联到具体会话及数据片段。

例：失火码与对应运行数据只能提出检查点火、供油、进气或机械状态的方向，不能仅凭 P0301 就宣布“一缸点火线圈坏了”。冻结帧和当前实时值须显示为不同时间的证据；未知量不填零，无响应不算无码，不能因 DME 无排放码就显示“全车健康”。

码库先针对 981 手册来源逐条审核、保留页码/原始码/适用模块/核验状态，再进入可查询知识层。新建知识结构应支持车型、ECU、完整厂商码与通用码的关联，不直接覆盖原 `code` 主键记录。诊断阈值优先来自对应 ECU 的维修资料；经验规则标为待验证。

AI 若增加，先限定为本地会话解释与资料引用，不让模型生成任意写车报文；仍遵守 Windows 本机与不上传云的数据约束。

## 5. X431 怎样用作中间采集工具

### 最有用的三类证据

1. **车辆/ECU 基线**：实车 ECU 清单、模块身份、完整 DTC、环境数据、当前编码与功能适用性。菜单目录和历史会话只作索引。
2. **测量值对照**：X431 显示的名称、单位、数值和时间标记，与同一次会话的请求/响应同步。用来确认 DID、字节序、缩放、状态枚举和缺失值。
3. **单功能全过程**：开始前读取、进入功能、实际执行、结束后回读以及实际效果；保留 X431 车型软件版本、ECU 身份、操作前提和所有负响应。涉及设码时记录一项变化，不能把多个同时变化的结果归因到一个字节。

先检查 X431 本机是否能导出上述明文。报告 PDF、数据流回放和诊断反馈日志并非同一层数据；没有检查日志内容前，不声称它包含可重放 CAN 帧。本轮未连接 X431，也未验证其导出格式。旧归档提到的解密/运行时 hook 研究不作为本方案前置步骤。

### 外部监听方案

如果 X431 没有可用的原始通信明文，可在已确认的诊断总线上并联独立采集器：X431 做唯一主动诊断端，采集器为硬件 listen-only。本项目此时停止主动轮询。PEAK 官方提供 listen-only 能力；CSS 的采集/逆向工具文档提供日志与信号对照方法。[PEAK ListenOnly](https://www.peak-system.com/documentation/API/PCAN-Basic.Net/html/3e5e1a2d-b990-4cc6-9908-001585cd3871.htm)、[CSS CAN 采集与逆向](https://www.csselectronics.com/pages/can-bus-sniffer-reverse-engineering)

分线器、总线引脚、电气连接和终端电阻须按设备说明与本车线束确认；不要照抄其他车型接法或额外并入终端。OBD 插座上的可见诊断通信不等于车内所有总线广播；若网关后某段不可见，先确认拓扑，不盲目移接车内总线。ELM 的 monitor 模式不自动满足完整抓包要求，需要验证丢帧、时间戳与长帧重组能力。

每份本地采集包建议保存：

- `manifest.json`：脱敏车辆标识、ECU 身份、X431/适配器版本、时间基准、采集位置和条件。
- `frames.jsonl`：单调时间戳、总线、ID、标准/扩展帧标志、DLC、原始字节、错误/溢出计数。监听记录的物理方向若未知应标未知，不伪造 tester/ECU 来源。
- `events.jsonl`：用户操作与 X431 显示值的时间标记。
- `transactions.jsonl`：离线关联后的请求/响应、ISO-TP 重组、服务/子功能、负响应及耗时。
- `before.json`、`after.json`：可读的完整目标配置及实际功能效果。

原始数据放 `.local/obd-captures/`，不提交 VIN、个人行程、访问凭据或整份专有库。提交仓库的是有来源的脱敏协议定义和回放用例。断帧/溢出记录不能当完整设码证据。

## 6. 从捕获到独立设码，真正缺什么

“隐藏功能”可能是编码位、自适应值或需要授权的功能；“特殊功能”可能是复位、学习、执行器控制或一整套有机械前提的维护程序；固件刷写又是独立项目。不能用同一个“发送命令”按钮承载所有操作。

每项可执行功能都要有独立定义：目标 ECU/软件版本、适配器要求、前置条件、会话状态、寻址、参数编码、允许变化的位、应答判据、完成判据、持久化回读以及失败恢复流程。对于 UDS，相关服务可能包括会话控制、数据写入、例程控制和安全访问；使用哪些服务必须以该功能证据为准。[CSS UDS 说明](https://www.csselectronics.com/pages/uds-protocol-tutorial-unified-diagnostic-services)

**不能直接重放一次抓包的原因**：若 ECU 使用挑战响应，当前 seed 需要对应 key；采集到一次 seed/key 并不等于获得适用于下一次会话的算法。`udsoncan` 也要求调用者提供安全算法和 DID 编解码器，并不附带 Porsche 解锁知识。[udsoncan 配置说明](https://udsoncan.readthedocs.io/en/latest/udsoncan/client.html)

独立使用的验收必须在 X431 完全断开后、重新建立的诊断会话中完成。若功能依赖在线授权、激活凭据或未知算法，记录为该项阻塞因素；不得把一次 X431 已解锁会话中的成功误判为“以后可独立使用”。不猜测密钥或对车穷举。

建议首个设码试点选择用户确实需要、可以完整读回与恢复、与行驶安全无关的单项舒适功能，具体项目待用户列出。PDK 学习、制动排气、驻车制动维护、转向标定、安全气囊和动力软件刷写不能用舒适设码试点的结果替代各自验证。

产品执行器需要：

- 执行前识别 ECU 与配置版本，读取当前完整块，检查计划差异；只修改已定义字段，保留未知位。目标身份或读回不匹配即不开始。
- 将供电、车辆静止、发动机状态等条件写入各功能定义，门限与操作前提来自对应维修程序，不拍脑袋使用全局数值。
- 持久记录阶段与结果。**超时不等于未执行**；结果不明时先重连核验，禁止自动重试写入。
- 区分“请求被接受”“例程执行完成”“编码回读一致”“重新建立会话后仍生效”。需要重启/点火周期的项目按已验证流程验收。
- 备份编码只支持相应配置恢复，不承诺恢复刷坏的 ECU。操作开始后的“取消”不能等同于拔线；中止行为需按功能定义设计。

## 7. 对应仓库的实施拆分

### A. 通信与回放基础

新增 `packages/obd` 承担适配器接口、传输、请求调度和协议解析；在 Electron 本地主进程或独立子进程运行。先做 vLinker FS BT 的 Bluetooth COM/RFCOMM 传输与回放接口，MX+ 不纳入联调；Panda 先做文件导入，PT3G 原生接入后置。COM 方案可使用 SerialPort，需针对当前 Electron 和 Windows 打包实测。[SerialPort Electron 文档](https://serialport.io/docs/guide-electron/)

暴露枚举、连接、断开、扫描、开始/停止采样与订阅状态的窄 IPC；renderer 不接收任意原始报文发送权限。连接状态区分“设备已连接”和“ECU 有效响应”。会话保留原始数据，回放驱动复用相同解析/展示链路。

验证：离线回放覆盖分块输入、多个 ECU、长响应、超时、乱序/截断和设备掉线；Windows 实机验证驱动与干净退出。没有真车时可以完成这一层，但不能宣称 Phase 2 验收通过。

### B. 标准 OBD 端到端

修改 `packages/db`：为会话补结束时间、来源、适配器固件与协议信息；扩展 DTC 来源/状态；新增样本、支持能力与事务引用。样本至少含会话、ECU、时间、服务/PID、原始值、物理值、单位、质量和解码版本。批量写入 SQLite，UI 节流。

接通 `ObdPage` 的连接、实时数据、故障码、就绪监控和实际车辆信息。手工输入与车上读取明确区分，读取里程或 VIN 不静默覆盖本地档案。

验证：与 X431 在可比工况下核对共同支持指标；“无码”必须有有效响应，插拔后旧值标过期；停止采样后不再发送请求，重开应用可回放原会话。记录实际采样率与缺失率，不能用模拟数据通过实车验收。

### C. 扩展诊断与本地分析

由已采集模块建立版本化定义；先做一个 ECU 的识别、DTC 与少量测量值，再扩到其他模块。补充经 981 来源核验的知识记录，输出可追溯检查建议。未知版本保留原始结果，禁止套错公式或故障解释。

验证：每项解码与 X431 名称、单位、数据对照；相同故障码在不同模块/车型下不互相覆盖；数据缺失时不产生确定性诊断。

### D. 独立设码试点

在功能和硬件已明确后，同步修订旧 ADR，并为一项功能实现可审查的操作计划、状态机、备份/差异、回读与恢复定义。离线回放只验证软件逻辑，写车能力还需合适台架或受控实车验证。

验收核心：目标身份匹配、单项变更、X431 断开后新会话独立执行、持久化核验与恢复验证。成功只计入该 ECU 版本下该功能，逐项扩大支持范围。

## 8. 尚需补齐的输入

1. vLinker FS BT 接通后记录系统接口、固件和身份；最初淘宝商品的完整型号仍待核实，但不再阻塞首期路线设计。无需将 RaceChrono 使用中的 MX+ 改接电脑。
2. 用户最优先的 2–3 项隐藏/特殊功能，明确期望前后行为。
3. X431 的准确型号、Porsche 软件版本、一次本机导出的 ECU 基线与数据流样本；comma4 连接后核实 Panda 服务接口、固件、总线映射、时间戳和静默采集能力；PT3G 的具体品牌/版本与驱动留作后续确认。
