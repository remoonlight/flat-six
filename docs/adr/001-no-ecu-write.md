## Current decision — adopted 2026-09-27, updated through 2026-10-04

On 2026-10-01 the user requested a combined 981/982 PIWIS maintenance/programming workspace, with 991.1/991.2 reserved in Markdown only. This authorizes project-owned catalog summaries, local plaintext rule inspection, offline workflow preparation and export. Roller routines and programming are feature-specific targets; their exact ECU applicability, access, requests, verification, exit and recovery remain unqualified. The workspace therefore has no new vehicle execution channel. See workspace scope（本机资料：`docs/piwis-workshop.md`） and 991 interface reservation（本机资料：`docs/piwis-991-interface.md`）.

The user explicitly requested reverse engineering X431 fault-code definitions, measurement definitions, and hidden-feature coding so the Windows project can ultimately communicate directly with the car through vLinker. Priorities are live engine parameters and X431 hidden features. This supersedes the previous permanent exclusion of protocol-data decoding and independent coding research.

This decision authorizes implementation of one constrained active operation: clear DTCs on the named 981 DME/Gateway profiles only. The topology action uses the direct-click decision below; CLI live clearing still requires explicit clear authorization. X431 must be inactive, and a read-only request must never clear. The chain is identity qualification, DTC read, durable pre-clear identity/DTC/raw snapshot (`pre-clear.json`, flushed and fsynced), one exact clear request, then a DTC reread. DME uses `14FF00` with KWP reference `54FF00`; Gateway uses `14FFFFFF` with UDS reference `54`. Those are protocol references from local inventory, [Scapy KWP](https://github.com/secdev/scapy/blob/master/scapy/contrib/automotive/kwp.py), and [udsoncan ClearDiagnosticInformation](https://udsoncan.readthedocs.io/en/latest/_modules/udsoncan/services/ClearDiagnosticInformation.html), not observed Porsche clear responses (`sourceObservedResponse=false`, `liveVerified=false`). Unknown payloads, uncertain sends, retries, coding, and all other ECU writes remain blocked. A clear snapshot is evidence, not a way to restore erased DTCs.

The standard engine set is a separate read-only path: qualify DME identity on the observed `7E0/7E8` pair, then configure the fixed standard Mode 01 `7DF/7E8` route, query `0100`, and only query the supported subset of `04`, `05`, `0C`, `0D`, `0F`, `11`. The old `1089` route has an observed `7F0111` failure; there is no automatic fallback or retry. CLI field evidence exists for the fixed standard route; the newly integrated desktop path still needs vehicle acceptance. Published formulas alone do not establish vehicle support. A malformed/failed response stops the run; it does not authorize a guessed address or session. The field procedure is vehicle-connection-runbook.md（本机资料：`docs/vehicle-connection-runbook.md`）.

- Offline inspection and extraction of the user's local diagnostic files, protocol definitions, replay, and a project-owned read-only transport are in scope. Raw vehicle logs and proprietary package files stay local under `.local/`.
- Current live execution is limited to explicitly defined read-only diagnostics plus the constrained clear-DTC operation above. An observed X431 request is evidence, not automatically an approved project operation. Unknown addresses, payloads, formulas, ECU versions, and coding values remain unknown.
- Independent coding is a product target, not a delivered capability. Each concrete feature needs its ECU/version applicability, read-before/write/read-back sequence, timing, integrity/security dependencies, failure behavior, and recovery procedure established before a controlled write validation. This request does not authorize speculative writes, firmware flashing, or actuator tests.
- X431 is a research reference. The final application must own its definitions and transport and must not depend on a running X431 session. On 2026-10-01 the user explicitly added OBDLink MX+ over Bluetooth as a project adapter; disconnect RaceChrono/OBDwiz before using the same adapter here. This supersedes the earlier MX+ reservation, without expanding authorized vehicle operations.
- Existing manual companion snapshots stay compatible. Their optional-before rule does not apply to future automated writes, which require an original-value backup.

The project now supports adapter enumeration/voltage and the existing named read-only diagnostic transport; its initial USB-only voltage was 0 V, and subsequent external-12-V samples were 11.635/11.642 V. No VNCI ECU reads have been validated. VNCI clear-DTC and coding remain disabled until separately qualified on this transport. The coding request retains the feature-specific identity, original backup, exact write/read-back and recovery requirements above. See VNCI USB evidence（本机资料：`docs/vnci-usb.md`）.

## Diagnostic CAN and internal CAN targets — 2026-10-04

The user clarified two connection purposes: diagnostic CAN should cover the car's diagnostic functions; an internal network such as Drive CAN should only receive its current bus data. These are product targets, not evidence that every adapter, ECU or write function is already qualified. Internal-bus receive mode must not send vehicle diagnostic, clear or coding requests; adapter-local monitor configuration is distinct. Network identity requires known physical mapping, not a device brand or successful Bluetooth connection.

The connection-settings questions are now closed. The user manually changes physical wiring; software uses the selected/remembered Drive CAN / ADAS CAN receive configuration without switching physical adapter channels or identifying the network automatically. Selection does not qualify wiring, bitrate, adapter receive capability or signal definitions. Internal receive runs continuously and resumes new data after reconnection, without diagnostic requests or invented samples. Diagnostic checking starts in system topology, following the car's X431 workflow. With an independently valid adapter link and a defined terminal no-response outcome, mark the unit nonresponding and continue other named candidates; do not infer absence or reconnect. Identity conflicts, unterminated responses, cleanup failure or uncertain link validity stop that stage, and negative responses are recorded separately. Actual diagnostic disconnects allow three connection attempts; within-budget recovery requalifies the current unit/restores its defined session before resending the unfinished read-only question and continuing. A later disconnect starts a new budget. Exhaustion ends that task while background adapter reconnect continues; later recovery must not restart the failed task automatically. Vehicle writes must not be replayed. Remembered purpose/adapter/CAN, available devices only, voltage `--` without invalidating verified communication, no silent adapter replacement, and truthful actual-close/disconnect states remain required. Final decisions are recorded in [convergence review](../convergence-review.md#连接设置本次确认与剩余质疑); implementation and capture/car validation remain incomplete, and these decisions do not qualify an adapter or authorize a new vehicle operation.

Topology must first identify responding control units and read valid DTCs. A clear click should process the identified units with DTCs individually, each with its own exact definition/version/transport qualification; unsupported, unidentified and failed-read units must not receive clear requests. The current implementation still only qualifies the named DME/Gateway paths above; this document-only request does not authorize speculative scanning or clearing other modules.

Ordinary read/display results should be transient and persisted only by an explicit Save Result action; changing selections discards the previous batch. The 2026-10-05 desktop path implements transient ordinary results and explicit complete-batch saving; mandatory pre-clear evidence remains separate. The latest nine answers confirm mandatory pre-clear identity/DTC/raw evidence and future fresh complete coding-original backups as persistence exceptions; failed durable backup blocks modification. Save Result retains the actual current acquisition process, not only its final value. No historical artifacts are deleted by this requirement.

For coding, the user explicitly requires reading the existing car coding and establishing its definition before any next step. Captured ECU-layer requests/responses and decoding behavior are the initial acceptance reference; X431 VCI/Bluetooth framing is not vLinker framing, and HCI-reassembled PDUs do not establish physical CAN timing. Reading/defining coding does not qualify a write, routine, actuator or flashing operation. Remaining decisions are recorded in [convergence-review.md](../convergence-review.md#实时-obd-本次确认与剩余质疑); the full local Markdown is `docs/obd-realtime-convergence.md`.

## Nine-answer scope update — 2026-10-04

The diagnostic support goal now includes all project 981/982 control units and X431 plus PIWIS functions, beyond a static catalog. The current 2014 981 evidence does not validate other variants; exact identity, definitions, adapter/firmware and feature-level acceptance remain required. The latest reply provisionally caps selection at 12 parameters in the current diagnostic unit; this is a product decision, not evidence of the X431 limit. Actual X431 limits/cadence still require verification and the full directory/internal receive scope remains intact. Project-displayed protocol, live-data, firmware and adapter support material and capabilities must also work after Windows installation/migration; this does not authorize publishing private captures or vendor originals.

Known diagnostic DIDs/request groups and verified passive-bus signal definitions should display vehicle values; optional Wireshark capture export must preserve the actual available layer without inventing physical CAN frames or timing. Internal CAN receives only and must not transmit vehicle CAN data; adapter-local configuration is distinct and actual silent-receive capability requires verification. Explicit terminal per-unit failures may be recorded before continuing other qualified batch targets; disconnect, identity conflict, uncertain/unterminated outcome or cleanup failure stops the batch. Writes are never automatically replayed; diagnostic read recovery retains the connection rules above.

X431 hidden/coding functions remain a full goal; DME Fuel Market is a named candidate, not an authorized default US-to-Europe change. The latest reply requires reading and durably saving vehicle original coding first, then analyzing its meaning, modifying target coding, writing it to the vehicle and reading back to verify. This covers the full X431 coding scope without requiring Fuel Market as the first pilot. Explicit start/stop streaming PCAPNG recording and passive decoded internal values are confirmed. Vehicle ECU firmware flashing is now an explicit development goal; adapter firmware upgrades are not newly added. Coding backup is not a full firmware backup, and flashing still requires a matching package, exact process, transport qualification, failure recovery and feature-level validation. On 2026-10-05 all three product proposals are resolved: retain the immutable first coding baseline and separate complete per-write identity/version/time backups; edit verified named fields and legal options with original/target/raw differences while preserving unchanged or unknown bytes; consider only matching original-manufacturer firmware files. Third-party/custom/tuning files are reserved for a separate scope, not automatically added as future required work. A first read baseline is not proof of factory-original coding. The user has confirmed the Restore Original Coding button applies only to the currently selected ECU, using its first complete coding baseline; no other ECU is restored. There is no new mandatory product choice in this discussion. The target behavior preserves a fresh current backup before restoration, requalifies identity/version and verifies by rereading; missing qualification must not be bypassed. ECU firmware flashing must use a verified actual wired diagnostic transport, with Bluetooth prohibited; wired capability alone does not qualify the head/package/ECU/process, and disconnect must not cause Bluetooth fallback or automatic write replay. This restriction is specific to ECU flashing and does not silently ban existing read-only Bluetooth use or qualify Bluetooth coding. The user has not verified internal receive/decoded display/saving; no new vehicle acceptance is inferred. Actual capability, exact definitions and validation remain incomplete. No upgrade, flash, new clear profile or coding write is authorized by this Markdown update.
